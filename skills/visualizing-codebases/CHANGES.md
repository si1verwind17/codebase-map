# Meaning-rules changes

Only changes that can make facts on an existing map wrong or incomplete go here: a meaning rule in SKILL.md, or a new kind of fact to look for. Viewer, scanner and schema changes do not (the page refresh and the full rescan cover them).
Bump `RULES_VERSION` in `scripts/vizcode/__init__.py` with each new section; prune old sections from the bottom when the file passes about 10. The oldest section left is the floor: a map older than it gets a full meaning re-check.

## Rules 6 — 2026-10-25
- Routes the scanner reads (SKILL.md § Run, the structure pass's lists; § Stack): more route styles are read: a class's verb methods each handle their route (`as_view()`, `::class`, a Resource added to an API), Flask decorators and `add_url_rule`, file-system routes (Next.js, SvelteKit, Nuxt), docblock annotations (Symfony `@Route`), chained route methods (gorilla/mux `.Methods`), and a path added to a name (`BaseURL+"/x"`, listed `(after ..)`); each route-looking line with no route needs a pattern or a `problems` entry. Write the requests and example keys of the new routes, drop `stack.yaml` patterns now listed `duplicates`, and resolve each `after` head like a mount's prefix.
- Route prefixes (SKILL.md § Run, the structure pass's lists; `stack.yaml` `base_paths`): prefixes now join across files and blocks (FastAPI `include_router`, Django `include()`, Flask blueprints, Rails `namespace` and `scope`, a router handed to a register function, a mount naming a router of its own file), and a prefix only config sets goes into `base_paths` once per deployable folder. Rewrite `request` keys and example keys that spell a route without its prefix, compose only the mounts and includes marked `not composed`, and drop routes on actions an `only:` leaves out.
- Route handlers (SKILL.md step 5, `references/stack.md`, § Stack): an inline function registered as a route, inside a function or at a file's top, is its own handler node named after the route; a route the framework registers ends at the line that turns it on, `inferred`, named in `problems`. Move the route's examples, pins and relations onto its handler and drop `problems` entries written to clear `route.file-handler`.
- Outbound requests (SKILL.md § Matching interactions, `summary.md` § Likely requests): `http clients` now lists calls through the code's own HTTP helpers and client classes, request descriptors (`{method, url}`), calls whose address is built (format calls, a held name, a path constant, a placeholder host) and each language's common clients (C# HttpClient, Go net/http, WebClient/RestClient, Locust), and § Likely requests pairs each with the route or rpc it likely reaches. Write the `request` for each pair the code confirms, drop hand-written requests the lists now give as facts, and clear each `request.unmatched`.
- gRPC requests (SKILL.md § Matching interactions): a gRPC client end is each call of an rpc on a stub, with that rpc's key alone. Move `request`s written from the method that builds a stub, or from a client registration (`AddGrpcClient`), onto the calling methods, and drop requests for rpcs nothing calls.
- Gateway routes (SKILL.md § Deployables, not folders, `summary.md` § Gateway routes): the routes proxy and API gateway configs send on are listed with their target and rewrite (nginx, Spring Cloud Gateway, Envoy, YARP). Write each as a `request` from the gateway's service to the target's, and check hand-written gateway requests against them.
- Jobs and messages (SKILL.md § Queues, `references/interactions.md`): `summary.md` lists the jobs defined and enqueued of the packs' job systems (Celery, RQ, Dramatiq, Sidekiq/ActiveJob, Laravel queues, Bull, Hangfire, Spring; aliased tasks, mailer `deliver_later`, a controller's dispatch, a job with no marker paired to `a class of that name`) and the broker messages published and consumed, by topic or queue (Kafka, RabbitMQ), paired in § Likely requests. Write the job-queue `event`s, the schedules' `batch`es and a `topic` node with its `event`s for each, and check hand-written ones against them.
- Tables (SKILL.md § Side effects, § Stack, § Matching interactions): table facts now come from ORM calls per method (ending `, read` or `, write`), repository and declarative-client interfaces (a call reads or writes the entity's table, Spring Data among them; a method only the library base supplies starts at the caller), an ORM's naming default for entity-looking classes (ActiveRecord, Django, gorm, Flask-SQLAlchemy), mapper XML statements, and the tables `.sql` files, schemas and migrations create. Attach the `db-read`/`db-write` from those methods, give each table a node where code reads or writes it, and check scripted or hand-written table relations against them.
- Deployables and modules (SKILL.md § Deployables, not folders): a browser app built into or served by the backend is a service of its own; a package run as several roles is one service per role, a relation between roles starting at the making role's service with `via`; services of one module that builds several deployables each claim their `packages`; every build.sbt gives its projects as modules; a Rust `impl` in another file sits under the struct its module declares; stock database, broker or monitoring images, recipe folders and test, CI, docs or dev images are no deployables, and a large unscanned share is one. Move relations and `via`s onto the methods now under each service, re-point services, pins and examples that named a split module or a per-file class, and drop services or `problems` entries written only to clear a warning that no longer fires.
- Stack lines (`references/stack.md`): a `telemetry` line goes into `ignore` unless the map shows the telemetry flow; one entry for a shared prefix covers its lines.
- Credentials in source (SKILL.md § Never read secrets): a credential literal met in source is cited by `file:line`, never repeated; remove one an existing map or its notes quote.

## Rules 5 — 2026-10-21
- Job triggers (SKILL.md § Deployables, not folders): a job that triggers a job of its own service is a `batch` relation too, from the calling job's method to the target task method, keyed `task <name>`; turn a `problems` entry that records such a trigger into that relation.
- Generic jobs (SKILL.md § Matching interactions): a job whose tables come from its inputs is one relation per direction with a wildcard key and the concrete tables in `tables`, also when every caller passes literal tables; merge relations written one per table into that one.

## Rules 4 — 2026-10-21
- Route keys (SKILL.md § Stack): a path parameter is written `{name}` whatever the framework writes around it (`{id:int}`, `{id?}`, `{*id}`, `:id(\d+)` → `{id}`), and a route's path already holds the prefix of a mount in its own file that the scanner joined (`composed onto N routes` in `summary.md`): rewrite `request` keys and example keys that spell a route otherwise.
- Route handlers (SKILL.md step 5): a route whose handler is a file or the function that registers it (`route.file-handler`, `route.setup-handler`) gets its real handler from a `stack.yaml` handler group, or a `problems` entry saying why there is none.
- Deployables (SKILL.md § Deployables, not folders): a deployable in a language the scanner does not read is a `service`, not an `ext:` placeholder (clear each `deployable.unscanned`); deployables come from whatever runs things (manifests, charts, app-host code, a `Procfile`, a worker command); a gateway's config-declared route is a `request` from the gateway service; a store or service chosen per deployment is `deployment_dependent` with every alternative listed.
- Queues in a store or a job system (SKILL.md § Queues in a store or a job system): a list or stream in a datastore, a job queue or a table used as a queue is a `topic` backed by that store; a job queue's events are keyed `job <name>` on both sides.

## Rules 3 — 2026-10-20
- A call's direction (SKILL.md § data): a `request` now defaults to `data: forward`, and a `request` or `ext-call` set to `both` because of what the call returns goes back to `forward` (the `data.two-way-call` warning lists them). Only a flow both ways is two-way, as a `bidirectional` stream.

## Rules 2 — 2026-10-15
- In-process queues (SKILL.md § In-process queues): where a trace stops at a put on a queue, channel or hub that a background task drains, add the `in-process-queue` node and its `hand-off` relations; clear each `queue.missing` warning.
- Actor and entity messages (SKILL.md § Matching interactions): where a trace stops at a send to an actor or sharded entity, add the `request` to the handler it dispatches to.
